# Devlog - 2026-07-30

## The pivot: binary decoding instead of image extraction

The original plan ([devlog_20260725.md](devlog_20260725.md),
[HANDOFF.md](HANDOFF.md)) was to reverse-engineer map data from rendered
overview-map *screenshots*. That was abandoned: the real shareware data
files (`MAPHEAD.WL1`/`GAMEMAPS.WL1`/`VSWAP.WL1`) are freely
redistributable, already sitting in `orig/data/`, and decoding them
directly is exact (no pixel classification, no ambiguity between
similar-looking wall/floor textures) where image extraction would only
ever be an approximation. The project also moved from
`/home/smith/Desktop/wolf3dmaps` to `/home/smith/Agon/mystuff/Wolf3dOrig`
and became a real git repo somewhere between then and now (exact point
not recorded — a gap in the paper trail this entry is partly here to
close).

Current goal, per the Author: an end-to-end toolchain for authoring
**novel maps** that run under the real shareware `.EXE` — map geometry
(walls/doors/floors) and wall/door textures first; sprites and audio
later. Full scope and design lives in
[map_toolchain_notes.md](map_toolchain_notes.md), which is now the living
design doc for this effort (this devlog is a chronological log; that
doc is the up-to-date reference).

## What's built so far

- `src/toolchain/formats/palette.py`, `mapfile.py`, `vswap.py` — codecs
  for the Wolf3D palette, RLEW/Carmack compression + MAPHEAD/GAMEMAPS,
  and VSWAP wall/door textures. All grounded directly in
  `orig/src/WOLFSRC/*.C/H` and validated with round-trip tests
  (`tests/test_formats.py`) against the real shareware data files.
- `src/toolchain/cli/extract.py` — decodes the real shareware files into
  a wall/door texture sheet PNG and per-level tile-grid JSON dumps
  (`build/extracted/`, gitignored/regenerated).
- A project-local Python venv (`.venv/`) + `requirements.txt` (Pillow),
  since no Python dependency setup existed yet.
- **MapEdit 7.2** set up under DOSBox (`dosbox/mapedit.conf`) as a
  read-only cross-validation viewer. Important discovery: since v7.1 it
  deliberately refuses to export shareware-loadable `.WL1` files
  (anti-piracy measure by its author), so it can never be a build path —
  confirmed the custom Python compiler is the only route to a playable
  new level.
- Considered and rejected porting MapEdit's own Pascal source instead of
  using Tiled — it's tightly coupled to DOS-only APIs (`crt`, `dos`,
  BGI `graph`, a raw-interrupt `mouse` unit) throughout, not isolated
  behind a portable layer. Full reasoning in map_toolchain_notes.md.
- **Tiled 1.12.2** installed via Flatpak (not vendored, not the stale
  `apt` package) as the map-editing GUI. Project-scoped
  `src/content/maps/wolf3dmaps.tiled-project` created and tracked in git.

## Tiled export, done

Extended `extract.py` to emit a real Tiled tileset (`plane0_tileset.tsx`)
and per-level map (`level_NN.tmx`) from the decoded shareware levels —
`build/extracted/tiled/`. This settled `build.py`'s schema empirically
instead of by guesswork: GID equals the plane0 tile value directly
(tileset `firstgid=1`, no lookup table needed anywhere), and plane 1
becomes a Tiled *object* layer (point objects) rather than a tile layer,
since it's sparse markers — currently just the player-start marker, as
a `PlayerStart` object with a `facing` (`N`/`E`/`S`/`W`) property.

Validated two ways: Tiled's own `--export-map ... .json` round-trips the
generated `.tmx` with no parse errors and preserves the `PlayerStart`
object exactly, and the Author confirmed it visually — opened
`level_00.tmx` in the Tiled GUI and it renders as a coherent, correct
Wolf3D level. Full details in map_toolchain_notes.md's "Implementation
status" section.

Next: `build.py`, the reverse direction (Tiled `.tmx`/`.tsx` → WL1),
starting from this now-validated schema.

## build.py (Tiled -> WL1), first pass done

Wrote `src/toolchain/cli/build.py`: parses `level_NN.tmx` files with the
stdlib `xml.etree` (no new dependency), rebuilds plane0 straight from the
CSV GIDs, rebuilds the player-start plane1 marker from the `markers`
object layer, and calls `mapfile.build_gamemaps` to write
`MAPHEAD.WL1`/`GAMEMAPS.WL1` under `build/wl1/`. Also added a `levelName`
map property to extract.py's `.tmx` output so level names round-trip too.

Added `tests/test_build.py`: extract the real shareware data to Tiled,
build it back, and confirm plane0 and the player-start marker are
reproduced exactly for all 10 levels. All 9 tests pass.

**Known gap, since closed (see below)**: only the player-start plane1
marker round-tripped at this point -- enemies/items/pushwalls/etc. in
plane1 weren't part of the Tiled schema yet and were silently dropped by
`build.py`. Real shareware levels do have plenty of these (verified:
level 0's plane1 has 57 distinct non-zero values, not just the player
start). Extending the schema to cover them was the natural next step
whenever full level editing (not just structural validation) is needed.

## plane1 actors/items/pushwall schema, done

Closed the gap above. Grounded every other plane1 code directly against
`WL_GAME.C`'s `ScanInfoPlane()` switch (non-`SPEAR` branch only, since
this project targets the original WL1/WL6 episodes): guard/officer/ss/dog
stand+patrol at three difficulty tiers, unique bosses (Hans, Gretel,
Otto, Fat, Schabbs, both Hitlers), mutants, ghosts, static items/decor
(23-74), and the secret-pushwall marker (98). Highest code used: 259
(hard mutant patrol).

Rather than reimplementing VSWAP's sprite-chunk decoder (column-sparse,
masked -- a materially bigger task than the flat 64×64 wall-texture
format) just to get authentic-looking sprite art, `extract.py` now emits
a second Tiled tileset (`plane1_tileset.tsx`) of category-colored,
number-stamped placeholders (green=static item, orange=pushwall, dark
red=enemy any tier, purple=unique boss, pink=ghost, gray=unused code) —
full data fidelity, placeholder visuals. Since a Tiled map shares one GID
namespace across all its tilesets, this tileset can't reuse `firstgid=1`
like plane0 does; it starts at `firstgid=144` (`PLANE0_MAX_VALUE + 1`),
so GID = plane1 value + a fixed offset, still no per-value lookup table.
Each level's `.tmx` now has a second tile layer, `plane1`, alongside the
existing `plane0` layer and `markers` object layer — player-start cells
are always written as GID 0 there, since that data lives solely in the
`PlayerStart` object (avoids two disagreeing sources of truth for one
cell).

`build.py` updated to match: reads each tileset's `firstgid` from the
`.tmx` itself (not hard-coded), reconstructs the full plane1 grid from
the new tile layer, overlays the player-start object on top, and
rejects a few real mistakes clearly (a raw 19-22 code painted onto the
generic layer instead of using a `PlayerStart` object; a cell claimed by
both a `PlayerStart` object and a plane1 tile).

`tests/test_build.py` strengthened accordingly: the round-trip assertion
now compares the *full* plane1 grid (not just player-start positions)
and passes exactly for all 10 shareware levels. Validated the generated
`.tmx` still parses through Tiled's own `--export-map ... .json` with no
errors, with both tile layers and tileset GID ranges intact.

Remaining known gaps: plane1 placeholders are colored/numbered, not real
sprite art (see above); door lock-type still isn't distinguished in the
plane0 tileset (all doors share one flat placeholder color); `build.py`
still only compiles map data, not textures.

## plane1 mnemonic labels, done

The Author correctly read the raw plane1 numbers as switch-statement
dispatch codes and asked for short mnemonic labels on top of them (still
not real sprite art -- that stays a deferred, non-critical-path QoL TODO).
Added a name table to `extract.py`, grounded in `WL_GAME.C`'s
`ScanInfoPlane()` switch (GRD/OFC/SS/DOG/MUT stand vs. patrol, unique
boss names like HANS/HITLER/SCHABBS, ghost names, PUSH, PSTART-<facing>)
and, for the 49 static item types (tiles 23-71), `WL_ACT1.C`'s
`statinfo[]` table comments (puddle, barrel, 1up, clip, key1, etc.) --
tiles 72-74 are SPEAR-only slots in that table and unreachable in our
target WL1/WL6 games, so they stay unnamed (still correctly colored).
Each plane1 tileset tile now shows both the mnemonic and the raw code,
stacked. Purely a visual legend -- not stored or round-tripped, doesn't
touch `build.py`. Verified visually (`plane1_tileset.png`); all 9 tests
still pass.

## AgonWolf3D map translator, first pass done

The Author has a separate sibling project, `~/Agon/mystuff/AgonWolf3D` (a
from-scratch eZ80/ESP32 raycaster: discrete one-cell-per-input movement,
cardinal-only facing, its own MapMaker tool), and wants interop between the
two. Its map format is a genuinely different shape than real Wolf3D:
independent 15x15 "rooms" (not one continuous 64x64 grid) connected by a
room-transition graph, described by its own object catalog
(`src/mapmaker/tiles.txt`).

Per the Author's explicit choice (best-effort onto our *existing*
plane0/plane1 vocabulary, per-room, not a new from-scratch schema), built:
- `src/toolchain/formats/agonmap.py` -- reads Agon's `.map` binary (4
  header + 225 grid records, each a 5-byte little-endian int, Y-major/
  X-minor -- grounded in that project's own appendix-b doc and verified
  against a real file's raw bytes) and its tab-separated `tiles.txt`
  object catalog.
- `src/toolchain/cli/import_agon.py` -- maps each Agon object to the
  nearest-analog real Wolf3D plane0/plane1 code (walls by slot, "gold
  chalise"->chalice, enemies collapsed to stand/easy since Agon has no
  patrol paths or difficulty tiers, door orientation guessed from
  neighboring walls since Agon doesn't record it). Agon's numbered
  "room-link" doors become ordinary in-place doors that lead nowhere --
  the biggest acknowledged loss, since real Wolf3D has no room-transition-
  graph equivalent. Each translated room is embedded alone in a 64x64
  canvas (Agon's compiled 16x16 shape top-left, solid wall filler
  elsewhere) and written as `agon_<stem>.tmx` (a different filename
  pattern than `level_NN.tmx` so it can't accidentally get picked up by
  `build.py`'s glob).

Verified: all three floor-0 sample rooms (`00_0`/`00_1`/`00_2.map`)
translate and round-trip cleanly through Tiled's own `--export-map`
parser; `00_0` (the one with a start object) was renamed to `level_00.tmx`
and smoke-tested through `build.py`, confirming it *can* produce a real,
bootable WL1 level. `tests/test_agonmap.py` grounds the parsers against
real sample files (skipped if the sibling repo isn't present). All 11
tests pass.

Deliberately not done yet: exporting the other direction (this project's
Tiled maps -> Agon's `.map`/room-binary format) and whole-floor/room-graph
stitching -- both explicitly deferred by the Author for later.

## Major advance: AgonWolf3D room deployed as a real playable floor

Up to now every translator check was a data-level round-trip (parse ->
tmx -> Tiled's `--export-map` -> compare, or a throwaway smoke build in
`/tmp`). This time the translated `00_0` room was deployed for real:
swapped in as floor 1 (`E1L1`, `level_00.tmx`) in `build/extracted/tiled/`
(original backed up first), rebuilt through `build.py` into
`build/wl1/MAPHEAD.WL1`/`GAMEMAPS.WL1`, copied into the `build/playtest/`
DOSBox sandbox, and booted -- so starting a brand-new game now drops the
player straight into the AgonWolf3D room, no cheats/level-warp needed. The
Author confirmed the layout looks reasonably accurate.

This is the milestone that proves the whole pipeline end to end for
externally-authored content, not just for round-tripping the original
shareware levels: an entirely different game's map data can be carried
all the way into a booting, playable real Wolf3D floor. The swap itself
lives only in gitignored `build/` scratch dirs (reproducible any time by
rerunning `import_agon.py` + `build.py`, since `extract.py` would
otherwise clobber `level_00.tmx` back to the original floor 1 on its next
run) -- nothing about the real Episode 1 data is permanently altered.
