## Project Goals

The long-term aim of `wolf3dmaps` is to turn the classic Wolfenstein 3D
overview map images (now organized under
[src/assets/maps/orig](../src/assets/maps/orig)) into a machine-readable
map definition — a structured, versionable format (grid/tile data, wall
types, and object/actor markers) that downstream tools (renderers,
editors, analyzers, etc.) can consume without ever touching a raster
image again.

Each source image is a top-down render of one level: textured wall tiles
(wood, stone, blue brick, etc.) laid out on a grid, with small colored
pixel markers scattered through the rooms denoting special
entities — enemies, items, doors, and the player start position. The
extraction pipeline will need to:

1. Detect the tile grid and its dimensions from the image.
2. Classify each tile by wall/floor type based on texture/color.
3. Detect and classify the colored marker pixels (actors/items/start)
   and record their grid coordinates.
4. Emit the result as a structured, machine-readable format (e.g. JSON)
   per floor.

## Today's Goal

Start small and iterate: build and validate the extraction approach
against a single, known map before generalizing.

- [ ] Extract a machine-readable map definition from
      [Episode_1/0.png](../src/assets/maps/orig/Episode_1/0.png)
      (Episode 1, Floor 1 — the first map of the game).
- [ ] Validate the definition visually/structurally against the source
      image.
- [ ] Once the approach is proven on this map, iteratively extend it to
      the remaining floors of Episode 1, then the other five episodes.

The guiding principle for the rest of the project: get one map fully
right before scaling the extraction across all 60 floors.

## Reference source code (external, not vendored)

The original id Software Wolfenstein 3D source release
([id-Software/wolf3d](https://github.com/id-Software/wolf3d)) has been
cloned locally for reference at `~/Agon/id/wolf3d` — **outside** this
repository, on purpose.

`wolf3dmaps` (and its eventual sibling engine/game projects for the
ESP32-based VDP + eZ80 application) is its own standalone repository.
It is not a fork of id's source, and none of id's source is vendored,
copied, or republished here. The clone at `~/Agon/id/wolf3d` exists
only so we can read/consult the original format and engine logic as a
reference while writing our own independent implementation from
scratch.

This matters because id's release is under a **Limited Use Software
License Agreement** (see `LICENCE.DOC` in that repo), not a
permissive/open-source license — it grants "Educational Use" (adapt
routines to build your own software) but forbids duplicating or
redistributing the Source Code itself. Keeping the reference clone
fully separate from this repo's history and codebase is a deliberate
boundary to avoid any risk of this project (or its eventual publication)
being on the hook for redistributing id's source under an incompatible
license.

## Reference game data (shareware episode 1)

Also fetched the actual shareware episode 1 game data (the Wolf3D
equivalent of a Doom `.WAD`) from the Internet Archive's long-standing
mirror — [archive.org/details/Wolfenstein3d](https://archive.org/details/Wolfenstein3d),
id Software's v1.4 shareware release, which id has always permitted to
be freely redistributed. Extracted locally to `~/Agon/id/wolf3d-shareware`
and symlinked into the workspace as
[wolf3d-shareware-data-EXTERNAL](../wolf3d-shareware-data-EXTERNAL) —
same external/not-vendored treatment as the source clone, kept out of
git via `.gitignore`.

Key files now available for a real binary decode, should we pursue
that path alongside/against the image-based extraction:

- `MAPHEAD.WL1` — level offset table + RLEW tag.
- `GAMEMAPS.WL1` — compressed Plane 0/1 tile data, 10 levels (Episode 1
  only, per the shareware restriction).
- `VSWAP.WL1` — wall textures (64x64) and sprites.

## Open Questions for the Author

Before (and while) building the extractor, the following design
decisions need input from the Author. Check each box off as it's
resolved; feel free to answer inline or in follow-up devlog entries.

1. [x] **Output format** — Is JSON the preferred machine-readable
       format for the per-floor map definition, or would you rather
       have YAML, a custom binary/TSV format, or something matching an
       existing Wolf3D map format (e.g. the original `MAPHEAD`/`GAMEMAPS`
       layout)?
       - **Decision:** JSON. Where it doesn't compromise the schema,
         favor single-line, tabular-looking rows (e.g. one array/object
         per row of tiles) to keep the raw file readable at a glance.
         Exact formatting left to implementation discretion — subject
         to Author override if the result isn't legible.
2. [x] **Grid resolution** — Do we know the tile grid dimensions ahead
       of time (e.g. classic Wolf3D levels are 64x64), or should the
       extractor infer grid size purely from the image?
       - **Decision:** Confirmed 64x64 — comfortably within the 256x256
         tile ceiling imposed by the ultimate target platform (an eZ80
         assembly application), so no constraint-driven map surgery is
         needed for now. Should a future map ever threaten to exceed
         256x256, we'll revisit — either relaxing the target constraint
         or adjusting the map to fit. Tile pixel resolution is assumed
         consistent across all floor images, so [Episode_1/0.png](../src/assets/maps/orig/Episode_1/0.png)
         can serve as the prototype for grid-detection logic.
3. [ ] **Tile taxonomy** — Should wall tiles be classified by their
       in-game texture name (e.g. `greystone`, `wood`, `bluestone`), by
       a generic numeric/enum ID, or both (ID + human-readable label)?
4. [ ] **Marker taxonomy** — What's the full legend of colored markers
       we should expect (enemies by type, treasure, weapons, doors,
       push-walls, player start/facing, elevator switches, etc.)? Do you
       have a reference legend/key image, or should we reverse-engineer
       it empirically from the maps?
5. [ ] **Coordinate system** — Should the origin `(0,0)` be top-left,
       bottom-left, or match the original game engine's coordinate
       convention?
6. [ ] **Ambiguous/overlapping tiles** — How should we handle doors,
       secret push-walls, or elevator tiles that may render similarly
       to plain walls/floors in the overview image?
7. [ ] **Player facing/orientation** — Does the overview image encode
       the player start's facing direction, and if so, should that be
       captured in the schema?
8. [ ] **Tooling/language** — Any preference for the extraction
       tooling (e.g. Python + Pillow/OpenCV vs. a Node/TS image
       library), given the rest of the repo lives under `src/`?
9. [ ] **Output location & naming** — Where should generated map
       definitions live (e.g. `src/assets/maps/extracted/Episode_1/0.json`),
       and should the naming scheme mirror the `orig/` structure we just
       set up?
10. [ ] **Validation strategy** — Beyond visual inspection, do you want
        an automated check (e.g. re-render the extracted definition
        back into an image and diff against the source) to confirm
        fidelity?
11. [ ] **Schema versioning** — Should the map definition include a
        `schemaVersion` field so the format can evolve without breaking
        older extracted maps?
12. [ ] **Non-uniform images** — Should we assume all 60 floor images
        share identical dimensions/scale, or do we need to detect
        per-image scale (e.g. if the overview map was rendered at a
        different resolution)?
13. [ ] **Overview file** — Does [Overview.png](../src/assets/maps/orig/Overview.png)
        need its own extraction pass (e.g. episode/level graph, secret
        level connections), or is it purely cosmetic/out of scope for
        this effort?
