# Devlog - 2026-07-30 (Agon VDP merge-feasibility research)

Companion to [devlog_20260730.md](../../doc/devlog_20260730.md) (toolchain
work) and [agon_port_notes.md](../../doc/agon_port_notes.md). This entry
tracks a separate
thread: before writing a clean-sheet Carmack-style renderer for the Agon
VDP (`wolf3Dport`), we want to know whether it could ever realistically be
upstreamed into `AgonPlatform/agon-vdp`. That means not colliding with
existing/planned VDU commands, following upstream coding conventions as
closely as possible, and not reimplementing functionality that already
exists in that codebase.

Two companion docs hold the growing detail so this log doesn't become
unwieldy: [vdp-coding-conventions.md](vdp-coding-conventions.md) (style/
convention mining, items 10-13, 19) and
[vdp-3d-pipeline-reuse.md](vdp-3d-pipeline-reuse.md) (existing 3D/transform/
graphics-pipeline functionality worth reusing, items 14-18).

Numbering below is fixed/durable — items keep their number even if others
are added, removed, or ticked off. Don't renumber existing entries.

## Facts gathered so far

- **1.** Local checkout `~/Agon/mystuff/agon-vdp` has three remotes:
  `upstream` = `AgonPlatform/agon-vdp` (the real upstream), `origin` =
  `bgates747/agon-vdp` (this fork), `fab-vdp` = `tomm/agon-vdp` (the
  emulator's VDP source, used for the native userspace build).
- **2.** No `CONTRIBUTING.md`, style guide, or `.clang-format` exists
  anywhere in the repo (checked to depth 2 at minimum). Conventions are
  unwritten.
- **3.** `video/agon.h`'s `BUFFERED_*` opcode table has large free gaps:
  `0x1B`-`0x1F`, `0x2A`-`0x2F`, `0x31`-`0x3F`, `0x42`-`0x47`, `0x4A`-`0x4F`,
  `0x52`-`0x7F`, `0x81`-`0xFF`. Pingo occupies `0x49` (plus its own
  subcommand `41` for render-complete notification) — a fork-local
  allocation that would itself need reconciling against upstream before
  any real PR.
- **4.** Pingo's own integration is the closest worked example in this
  codebase of "add a large subsystem without touching the core dispatch
  surface": it claims exactly one top-level buffered opcode and
  multiplexes everything else as subcommands underneath it.
- **5.** The community docs site (`agonplatform.github.io/agon-docs`,
  cloned locally at `~/Agon/agon-docs`) is the human-facing command
  reference upstream maintainers actually care about, separate from
  whatever any one branch's `agon.h` currently says.
- **19.** Per the Author, `video/` has a de facto gatekeeper: Steve Sims
  ("ss7"/"sims"), who isn't an official maintainer in any formal sense but
  is generally acknowledged as the one who decides what gets merged, and
  who authors an estimated 90%+ of the code under root `/video`. He's put
  it more gently than that summary suggests — roughly, that a change
  should fit naturally with how things are already done there — which
  makes his commits the single best source for the convention-mining in
  items 10-12. Jeroen Venema ("evenomater") is another prominent
  contributor with his own side projects, including a bespoke `ez80asm`
  assembler targeting the Agon that runs natively under MOS on hardware
  and also ships a Linux-compatible binary (already noted in the handoff
  docs). Both are worth mining specifically by author, not just by
  recency.
- **20.** Checked `upstream/main` (tag `v2.16.0`) `video/agon.h` directly
  (item 6/T1). Its `BUFFERED_*` table: `0x40` compress, `0x41` decompress,
  `0x42`-`0x47` free, `0x48` expand-bitmap, `0x49`-`0x4F` free, `0x50`/
  `0x51` add/remove callback, `0x52`/`0x53` commented-out placeholders
  for a future timer-callback pair, `0x54`-`0x7F` free. Two takeaways:
  Pingo's `0x49` isn't an upstream allocation at all, just this fork's
  local addition on top of `0x48`, so it's a fork-collision concern, not
  an upstream one; and the block immediately above it, `0x4A`-`0x4F` (6
  codes), is genuinely free upstream too and a solid first candidate —
  but `0x52`/`0x53` should be treated as already spoken-for despite being
  commented out, since upstream clearly intends to fill them later.
- **21.** Two more local repos are directly relevant reference material for
  writing assembly apps that emit VDU command streams and talk to custom
  VDPs: `~/Agon/mystuff/AgonMaths` (canonical home for the Author's math
  routines, including an eZ80 integer 3D transform/camera API) and
  `~/Agon/mystuff/pingoasm` (where active application development against
  the custom Pingo VDP actually happens — hand-written eZ80 clients doing
  object/camera transforms, VDU emission, and, notably, real usage of a
  render-complete callback contract on Pingo subcommand 41, tying directly
  into item 15's callback-reuse question). Both are worth treating as a
  source of proven idioms when the Wolf3D VDP work reaches its own eZ80
  client/app side, not just the VDP firmware side.
- **26.** A second, separate qualifier from Steve, worth taking just as
  seriously as convention-fit (item 19): whether a proposed addition is
  likely to see broad use, versus serving one person's niche project.
  This isn't just a taste preference — the Agon has real, tight memory
  constraints. The firmware itself already consumes roughly half of the
  8MB PSRAM/SRAM budget, leaving on the order of 4MB for program buffers,
  and the Author's own programs already push that remaining budget hard
  enough to misbehave under load from asset data alone. Any new mainstream
  VDP feature competes for that same shrinking headroom across every
  program on the machine, not just this one, so "is this generically
  useful enough to earn its keep" is a legitimate bar to clear — not
  just a matter of taste. This bears directly on item 25's completion-
  notify proposal: it needs to be framed and scoped as a broadly useful
  primitive, not a Pingo-specific convenience, to have a fair shot.
- **27.** Another project standout worth highlighting: tomm8086, who
  owns and maintains `fab-agon-emulator` (this repo's `fab-vdp` remote,
  `tomm/agon-vdp`, tracks his fork's native/emulator VDP source; devlog
  item 1) and has also contributed to MOS and VDP proper, beyond just the
  emulator.

## Options considered

### Avoiding collisions with existing/planned VDU commands

- **6.** Diff this fork's `video/agon.h` against `upstream/main`'s (not
  just read this branch) to find every fork-local opcode added since
  divergence, before picking a number for anything new.
- **7.** Cross-check the community docs site's command reference as the
  human-facing contract, since it may reflect intent not yet in any one
  branch's source.
- **8.** Search upstream issues/PRs for in-flight opcode proposals or
  explicit allocation guidance, so a chosen byte doesn't collide with an
  unmerged PR.
- **9.** Prefer the existing buffered-command extension pattern (one
  reserved top-level opcode, subcommands multiplexed underneath, same
  shape as Pingo's `0x49`) over inventing new top-level `VDU 23,0` space —
  lowest collision risk and already proven/idiomatic in this codebase.

### Following upstream coding conventions

- **10.** Since no written guide exists, mine 3-5 diverse *recent*
  upstream (not fork-only) feature commits for naming, header-guard
  style, `debug_log` vs `force_debug_log` usage, error-handling idioms,
  and comment tone — one sample risks copying a fork-local quirk instead
  of the real convention.
- **11.** Check deeper in the tree for machine-enforced formatting
  (nothing found at root) before assuming convention-only, unenforced
  style.
- **12.** Read maintainer review comments on merged upstream PRs — often
  the real de facto standard even when undocumented anywhere.
- **13.** Use the Pingo integration as a structural template (own
  subdirectory, own docs, own native test harness, own build hooks) since
  it's the closest analog for organizing a large added subsystem in this
  fork, even though Pingo itself isn't upstream either.

### Reusing existing functionality instead of reimplementing

- **14.** Check whether existing buffered-transform commands (`0x20`/
  `0x21` affine, `0x28` transform-bitmap) already express "scaled/
  transformed bitmap blit" well enough for wall-column rendering, instead
  of writing a new rasterizer.
- **15.** Check whether the existing callback/notification mechanism
  (`0x50`/`0x51`, plus Pingo's own subcommand `41`) is generic enough to
  reuse for a render-complete signal, instead of inventing another one.
- **16.** Inventory the existing sprite/bitmap subsystem
  (`vdu_sys_sprites`) for any existing scale/stretch blit support —
  directly relevant to Wolf3D-style perspective-scaled wall textures.
- **17.** Check the vendored `vdp-gl`/`userspace-vdp-gl` library for
  existing fast blit/line-drawing primitives usable directly from the
  ESP32 side.
- **18.** Check existing audio and keyboard/mouse VDU exposure for what
  the game loop can already use unmodified, before assuming new commands
  are needed there too.

## Suggested sequencing

Opcode/collision audit first (fast, mechanical, de-risks everything
else), then the reuse inventory (determines how much new code is even
needed), then convention mining last, scoped only to whatever new code
the reuse inventory says must actually be written.

## Decisions and outcomes

- **23.** Decided: `0x4A` is the candidate top-level `BUFFERED_*` opcode
  for the future Wolf3D VDP extension (item 20). It's free on both this
  fork and `upstream/main`, sits directly above Pingo's fork-local `0x49`
  without touching it, and stays clear of the `0x52`/`0x53` timer-callback
  placeholders. Not yet written into any `agon.h` — this is a documented
  intent, not a code change.
- **24.** T2 done via the community docs site. Its Buffered-Commands-API
  reference confirms command 80/81 (`0x50`/`0x51`) is a real, documented
  general callback mechanism (VDP 2.12.0, expanded 2.15.0), but its event
  types are a closed enum (VSYNC, mode change, keyboard, mouse, palette
  change, read-pixel, VDP-protocol send/receive) with no generic "async
  operation complete" type. That's precisely the gap Pingo's command 41
  fills ad hoc — strengthens the Codex handoff's suggestion (its item 6)
  that a new callback event type is a real upstream-proposal candidate.
  Full detail moved to [vdp-3d-pipeline-reuse.md](vdp-3d-pipeline-reuse.md)
  item 6 and [vdp-coding-conventions.md](vdp-coding-conventions.md) rather
  than duplicated here.
- **25.** Decided (also recorded in `agon-vdp`'s `CODEX_PINGO_HANDOFF.md`,
  since it's relevant to both projects): don't build on `0x50`/`0x51` as a
  substitute for Pingo's command 41 — the fixed event-type enum (item 24)
  doesn't cover it, so 41 stays as-is for now. The real fix — a generic
  "async operation complete" notification — is a strong candidate for its
  own upstream pull request as a first-level VDU command in its own right,
  not just a Pingo-scoped fix; it's too broadly useful to leave as a
  Pingo-only workaround. One workable general shape: "when the next full
  command finishes executing, notify that it is done" — completion tied
  to command execution generically, not to any one subsystem.
- **28.** T8 done: the Author reviewed several of Steve Sims's own issues
  on `agon-vdp` (going back to 2024) as public feature-direction musings —
  self-authored "Consider: ..."-style proposals, often with no other
  participants. Sampled issues: #346 (swap variant of rectangular copy/
  move PLOT), #340 (winding-rule triangle fill for back-face culling —
  logged as a Pingo watch item in `agon-vdp`'s `CODEX_PINGO_HANDOFF.md`
  item 7), #335 (bitmap/sprite info query VDP variables — open since Nov
  2025, no PR, logged as a followup in `CODEX_PINGO_HANDOFF.md` item 8).
  No dedicated Discussions board exists for `agon-vdp`/`agon-mos`
  (`/discussions` 404s on both); Issues is the de facto forum.
