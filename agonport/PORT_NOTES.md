### Emulator and VDP products

Fab does not execute the ESP32 `firmware.bin`. For a custom VDP it loads a
host-native shared object (`vdp_<project>.so`) compiled with `USERSPACE` and
Fab's compatibility layer. A normal VDP feature therefore has two builds:

1. Native `.so` for Fab integration and desktop testing.
2. ESP32 `firmware.bin` for physical Agon hardware.

The initial emulator profile will deliberately use Fab's stock VDP. This
establishes a known-good executable/MOS/SD-card/profile baseline before any
custom module is introduced. A later custom-VDP launcher must use absolute
paths, launch from a directory with no fallback `firmware/`, pass `--vdp`,
`--mos`, and `--sdcard` explicitly, and prove that an invalid VDP path fails
closed.

All emulator/profile/launcher/documentation changes coupled to emulator
behavior remain uncommitted until the Author tests the emulator and explicitly
approves committing them.

### Physical VDP build and deployment

The upstream VDP firmware is a PlatformIO project using environment
`esp32dev`; `platformio.ini` selects Espressif32 6.6.0, Arduino, 240 MHz CPU,
80 MHz flash, QIO flash mode, PSRAM, and C++17. The hardware product is
`.pio/build/esp32dev/firmware.bin`.

For normal firmware deployment, place `firmware.bin` at the FAT32 SD-card root
and the latest official `flash.bin` at `mos/flash.bin`, then run
`*flash vdp firmware.bin` on hardware. The currently installed VDP must support
in-system flashing (1.04RC3 or later); known problematic updater releases are
2.8.0, 2.12.0, and 2.13.0. PlatformIO upload over a USB data cable is the
supported development alternative. Hardware functional review remains the
verdict for firmware behavior and timing.

## 2026-07-30: Render target design and original screen-layout terminology

Design decision for the Agon port's renderer: RGBA2222 (64-color) bitmaps as
both texture sources and render target(s), at 320x240, double-buffered.
Original DOS resolution/layout differs and isn't being carried over as-is.

Terminology from the original source
(`orig/src/WOLFSRC`), used going forward so it can be referenced
consistently rather than re-described each time:

- **View window** — the 3D-rendered area. Original globals `viewwidth`/
  `viewheight`/`viewsize` (`WL_DEF.H`, `WL_MAIN.C`). Notably, the original
  `SetViewSize()` *centers* the view window in whatever screen space is
  available above the status bar rather than stretching it to fill that
  space — the classic full-size view window (256x144) did not fill the
  full 320x160 area available above the status bar on a 320x200 screen.
- **Status bar** ("status window" in a `WL_AGENT.C` section-header comment)
  — the fixed-height HUD panel (health/ammo/keys/etc.), `STATUSLINES` (40
  rows), asset `STATUSBARPIC`, drawn via `StatusDrawPic()`.
- **Play border** — the letterboxed margin drawn around a shrunk view
  window when the player reduces `viewsize` below max at runtime (F5/F6).
  `DrawPlayBorder()`/`DrawAllPlayBorder()`/`DrawAllPlayBorderSides()`
  (`WL_MAIN.C`, `WL_PLAY.C`).

Screen mode chosen: Agon mode 136 (mode 8 + 128), 320x240, 64 colours,
60Hz, double-buffered. Width matches the original's 320 exactly (1:1, no
scaling), but height (240) is 40 rows taller than the original 320x200 --
more than the status bar alone accounts for. Resolved per precedent from
the Author's parallel `AgonWolf3D` project: extend the status bar with an
extra strip at the bottom, styled to match the rest of the status bar,
to absorb the otherwise-unused 40 rows. This keeps the view window at its
original proportions/placement and gives the extended area double duty as
room for original-game enhancements and debug output.

## 2026-07-31: video/wolf3d/ subfolder plan and implementation language

Reviewed the original `WOLFSRC` layout for a subfolder analog and
concluded most of it doesn't map to VDP-side work at all -- `WL_AGENT.C`,
`WL_PLAY.C`, `WL_ACT1.C`/`WL_ACT2.C`, `WL_MENU.C`, `WL_STATE.C`,
`WL_TEXT.C` are game logic that stays on the eZ80; `ID_PM.C` (VSWAP
paging) is superseded by the existing Python toolchain's pre-converted
RGBA2222 assets; `ID_VL.C` (palette/mode setup) is just a `MODE 136` VDU
call. Only one part has a real analog: `WL_DRAW.C`'s raycast column loop
plus the `WL_SCALE.C`/`CONTIGSC.C`/`OLDSCALE.C` compiled-scaler family
(three CPU-tier-specific implementations of the same job originally --
Agon only needs one modern one). That maps to a single new subfolder,
`video/wolf3d/render/` (scaffolded, placeholder `README.md` only, no code
yet): given a screen column, texture ID + source column, and top/bottom
height, blits a scaled textured vertical strip into the render target.
Deliberately not adding a `math/` subfolder (mirroring Pingo's) yet --
that only makes sense if the VDP ends up doing ray/wall-distance math
itself, which is still the open eZ80/VDP renderer-boundary question in
`vdp-3d-pipeline-reuse.md`/`ARCHITECTURE_PRECIS.md`.

Implementation language: C++, not the original's plain C (plus inline
assembly for the scalers). The original's language choice was purely a
product of its era's compilers/CPU, not something worth preserving.
`video/` is overwhelmingly Steve Sims's C++ (camelCase, tabs -- see
`vdp-coding-conventions.md` items 2, 9), and Pingo -- the structural
template this work mirrors -- is C++ as well (`Texture`, mesh/scene
classes, etc.), as is vdp-gl. Writing new code in C would be an
immediate, visible departure from house style and undermine the
convention-fit bar (devlog item 19) that upstreamability depends on.

Subcommand numbering: reserving subcommand `41` under `BUFFERED_WOLF3D`
(`0x4A`) for the render-done callback, mirroring Pingo's own subcommand
`41` under `BUFFERED_PINGO_3D` (`0x49`) for the same purpose (confirmed
against `moveair-local`'s `render-async.inc` -- enable/disable via
`db 49h,41,<0|1>` plus a token, delivered through the MOS keyboard-vector
callback path). Parity between the two extensions for a shared job, and
keeps both aligned if a generic "async operation complete" callback
(devlog item 25) eventually replaces both.

## 2026-07-31: BUFFERED_WOLF3D dispatch landed; eZ80 test app under src/asm/

`agon-vdp-wolf3d` now has real dispatch code, not just scaffolding:
`BUFFERED_WOLF3D` (`0x4A`) in `agon.h`, a `Wolf3dControl` struct/dispatcher
in the new `video/wolf3d.h`, and a `case`/`bufferUseWolf3D()` pair in
`vdu_buffered.h`. Subcommand `0` prints a hello message (`debug_log`) as a
pure dispatch smoke test; subcommand `41` is `set_render_notification`/
`send_render_complete`, ported from Pingo's `video/pingo_3d.h` as closely
as the existing conventions allow (same mode/token shape, same
`send_packet(PACKET_KEYCODE, ...)` delivery, distinct `"W3DR"` wire magic
so it's distinguishable from Pingo's `"P3DR"`). `send_render_complete` is
not yet called from anywhere -- no render pipeline exists to call it from
yet. One convention had to be copied to even compile: `readByte_t`/
`readWord_t`/`send_packet` are private on `VDUStreamProcessor`, so
`tag_Wolf3dControl` needed the same `friend` declaration Pingo's
`tag_Pingo3dControl` already has. Verified with a full `pio run -e
esp32dev` build (succeeds; Flash 82.3%, RAM 13.6%).

eZ80 assembly source for hand-written test clients (as opposed to the
Python map/texture toolchain under `src/toolchain/`) lives at
`src/asm/`, project-root-relative, one subdirectory per app with a
tracked `src/` and a gitignored `tgt/` -- the same flat contract
`pingoasm`'s `apps/<app>/{src,tgt}` uses, reused here rather than
invented fresh. First app: `src/asm/wolf3d_hello/`, a standalone (not
`pingoasm`-dependent) smoke test that sends `VDU 23,0,&A0,0;&4A,0`
(hello) and `VDU 23,0,&A0,0;&4A,41,0,0;` (render-done notify, left
disabled) to prove the wire encoding, modeled on the MOS/VDU conventions
in `pingoasm/apps/moveair-local/src/jet.asm` without depending on that
sibling project's files. Assembles cleanly with `ez80asm`. Not yet run
against a VDP: the Fab emulator profile at `agonport/emulator/` only has
the stock VDP wired up (`vdp_stock.so`, from `~/Agon/fab-agon-emulator`'s
prebuilt firmware); building a custom `vdp_wolf3d.so` would need a
`userspace/` build harness like the one `agon-vdp-pingo-v216-userspace`
has, which doesn't exist yet for this fork -- deliberately deferred as a
separate task.
